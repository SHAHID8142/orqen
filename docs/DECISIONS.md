## D-012 | 2026-11-05 | APPROVED — String length policy: Unicode scalar values
**Context:** `echo_ping` validation used JavaScript `.length` (UTF-16 code units) on the frontend and Rust `.len()` (UTF-8 bytes) on the backend — inconsistent for Bangla text, emoji, and other multi-unit scripts (e.g. 150 "🙂" = 300 UTF-16 units / 600 UTF-8 bytes / 150 code points).
**Decision:** all cross-boundary string length limits count **Unicode scalar values (code points)**: Rust `chars().count()`, JavaScript spread iteration `[...value].length`. Composed emoji such as "👍🏽" (base + skin-tone modifier) count as two code points. Grapheme-cluster counting was considered and deferred: it would require `unicode-segmentation` + `Intl.Segmenter`, whose edge-case agreement is platform-dependent, for an arbitrary limit where consistency — not linguistic precision — is the requirement.
**Consequences:** both sides now accept or reject identically for any input; enforced by Unicode regression tests in `src-tauri/src/commands/app_info.rs` and `src/lib/ipc/appInfo.test.ts` (English, Bangla, emoji, whitespace, empty, exact-200, 201-over). Future string limits must reuse this policy.

## D-014 | 2026-11-05 | APPROVED — SQLite persistence stack (Phase 2)
**Context:** Phase 2 required reliable local-first persistence for projects, the selection and settings, owned by Rust, with minimal dependencies.
**Decision:**
- `rusqlite` with the `bundled` feature (SQLite compiled into the binary — no system library dependency, identical behavior on macOS and Windows).
- One connection behind a managed mutex (`DbState`); `journal_mode=WAL` + `synchronous=NORMAL` + `foreign_keys=ON` + `busy_timeout` 5 s.
- Hand-rolled transactional migrations over `PRAGMA user_version` (per-migration transaction, rollback on failure, re-run safe) instead of the `rusqlite::migration` helper — full control for rollback testing.
- Selection state lives in `settings.selected_project_id` with `REFERENCES projects(id) ON DELETE SET NULL`.
- `uuid` v4 for project IDs, `time` (RFC 3339) for timestamps.
- New dependencies: `rusqlite`, `uuid`, `time` (Rust side only; no new npm dependencies).
**Consequences:** database files live in the OS app-data directory and are gitignored; corrupted databases fail closed with recovery guidance (never auto-reset); the frontend receives full snapshots from every mutation, keeping UI and database converged.

## D-015 | 2026-11-06 | APPROVED — Atomic auto-select + serial mutation queue (Phase 2 remediation)
**Context:** review confirmed that project creation no longer selected the new project (a Phase 1 contract regressed in the Phase 2 rewrite), and the frontend's independent per-operation pending guards allowed overlapping mutations whose snapshots could apply out of order.
**Decision:** (1) project creation performs INSERT + selection UPDATE in one SQLite transaction and reads the returned snapshot inside the transaction — all multi-write mutations follow this pattern (select/delete included); (2) the frontend store serializes ALL operations (load/create/select/delete) through one queue: single in-flight request, strict issue-order application, queued-not-discarded requests, UI disabled while busy, and pre-queue rejections only for client-side validation and unavailable-state mutations (both surfaced as errors); (3) databases with a newer `user_version` than the application supports fail closed untouched.
**Consequences:** the Phase 1 creation contract is restored and pinned by Rust-side tests; stale snapshots are impossible by construction; a database written by a newer Orqen version cannot be damaged by an older one. See [LESSONS_LEARNED.md](LESSONS_LEARNED.md) L-015/L-016.

## D-016 | 2026-11-06 | APPROVED — Agent registry, discovery & verification design (Phase 3)
**Context:** Phase 3 required provider-independent agent support starting with Codex and Claude Code, without fake connectivity claims or arbitrary process execution.
**Decision:**
- Static, in-code registry (`src-tauri/src/agents/definitions.rs`) is the single source of truth: stable ids (`codex`, `claude-code`), display names, providers, adapter kind, executable names, and capability metadata where `execution`/`orchestration` are explicitly `false` until implemented.
- Discovery is PATH-based only (plus a fixed Windows extension allowlist — `PATHEXT` is intentionally not honored) and **never executes anything**; "found" means a regular file exists.
- Verification is an explicit user-initiated `--version` probe via `std::process::Command` (no user-supplied arguments, no environment overrides), with a 10 s timeout that kills the whole process tree, bounded output (first 64 KiB kept, remainder drained), and distinct failure states (timeout / spawn failed / nonzero exit / malformed output). Shell involvement is platform-scoped per D-017: shell-free on unix; on Windows `.cmd`/`.bat` targets run via `cmd.exe` by OS design.
- Main Agent preference is a nullable `settings.main_agent_id` (migration v2) validated against the registry in Rust; unknown stored ids are dropped on load with a local log.
**Consequences:** discovery status can never imply authentication or connectivity; the probe surface is one fixed command per registered agent; adding a future agent is a one-entry change to the definitions list plus tests.

## D-017 | 2026-11-06 | APPROVED — Async agent commands + platform-scoped shell claims (Phase 3 remediation)
**Context:** review confirmed that synchronous Tauri commands blocked the main thread during CLI verification, and that the "no shell" claim was false on Windows for `.cmd`/`.bat` targets.
**Decision:** (1) `verify_agent` and `discover_agent` are async commands delegating all blocking work (process lifecycle, PATH walk) to `tauri::async_runtime::spawn_blocking`; the main thread and async executor are never blocked; IPC validation stays synchronous; no database locks are held during probes. (2) The verification deadline covers the whole lifecycle — after the direct child exits, output readers get a 1 s grace period before the result is decided; descendants holding inherited pipes cannot hang verification; readers drain shared bounded buffers. (3) Shell claims are platform-scoped: shell-free on unix; on Windows `.cmd`/`.bat` executes through `cmd.exe` by OS design with Rust's hardened escaping — the fixed `--version` argument keeps the injection surface closed, and `.exe` candidates are preferred. (4) Windows behavior is covered by `#[cfg(windows)]` tests that cannot run on macOS and are marked unverified.
**Consequences:** slow or hung probes cannot freeze the UI; a hard app kill during an active probe can still orphan the (≤10 s) child (documented); Windows verification behavior remains to be machine-verified when a Windows environment is available.

## D-018 | 2026-11-06 | APPROVED — Process-group termination + reader abandonment bound (Phase 3 final remediation)
**Context:** review confirmed that timeout cleanup killed only the direct probe child, orphaning descendants (e.g. a spawned `sleep`) that kept the inherited pipes open — leaving abandoned reader threads blocked for the descendant's lifetime and polluting the detached-reader counter; and that the settings Retry control rendered inside the disabled preference fieldset, making recovery impossible exactly when needed.
**Decision:** (1) CLI probes spawn in their own process group (`process_group(0)`, unix); timeout, cleanup, and shutdown paths terminate the whole group with SIGKILL (`libc::kill(-pgid)`) — descendants cannot outlive the probe by holding pipes. (2) Windows keeps direct-child kill only (no std process-group API); the limitation is documented and the detached-reader counter (max 64, logged when exceeded) bounds the resource side. (3) Reader threads abandoned at the grace deadline close their read end at their next wakeup and release the counter on every exit path (EOF, error, abandon-break). (4) The Main Agent preference fieldset's error/recovery controls live outside the disabled fieldset; preference radios stay disabled until settings load successfully.
**Consequences:** timeout probes leave no orphaned pipe holders on unix (verified: zero lingering processes after the timeout suite); reader accumulation is bounded (≤64 threads × ≤64 KiB each) and readers self-release when descendants exit; the recovery UI is usable in the exact state it is needed for. Windows tree-kill remains a documented gap until a Windows environment can verify it.

## D-019 | 2026-11-06 | APPROVED — Enforced reader-slot admission limit (Phase 3 resource-safety correction)
**Context:** the Phase 3 detached-reader counter (MAX_DETACHED_READERS = 64) was advisory only — it logged when the count exceeded the bound but never prevented further allocation, so a misbehaving CLI whose descendants held the inherited pipes could accumulate unbounded blocked reader threads.
**Decision:** the counter is replaced by an **enforced slot pool** (`READER_SLOTS`, 64 slots): both of a probe's reader slots are reserved atomically before the probe spawns; an exhausted pool rejects the probe with a structured `ResourceBusy` error (user-facing message, no child started). Slots are plain RAII permits (`ReaderSlot` with a Drop that increments the pool) moved into the reader threads — capacity returns exactly when each reader thread terminates, however long descendants keep the pipes open. No new dependencies (a `Mutex<usize>` + ZST permit). The old detached-reader diagnostic counter was removed (the pool's `available_reader_slots()` covers diagnostics).
**Consequences:** concurrent CLI verification is genuinely capped at 32 probes; exhaustion surfaces as an accurate "verification is busy" error instead of unbounded thread growth; underflow/double-release are impossible by ownership (permits are non-Clone, moved into exactly one thread, dropped once). Windows keeps direct-child kill only — descendants may hold slots longer, but the admission bound and busy rejection behave identically.

## D-021 | 2026-11-06 | APPROVED — Test-only `test-timeouts` feature + absent-fixture test definitions (Phase 3 Feature 002 remediation)
**Context:** two test-integrity problems in the diagnostic execution suite. (1) The 120 s run deadline could not be exercised: waiting it out in a test is unacceptable, and a `#[cfg(test)]` override is invisible to integration tests (a separate crate that links the lib without `cfg(test)`). (2) The admission unit tests called `registry.start(find_definition("codex"))` — on any machine where the real `codex` CLI is installed, the spawned worker would discover and EXECUTE the real provider CLI, violating the rule that automated tests never run real coding agents.
**Decision:** (1) a Cargo feature `test-timeouts` (empty dependency list, never enabled by the app or release builds) exposes `TEST_DEADLINE_OVERRIDE` in the runner; `tests/execution_timeout.rs` is compiled only under that feature (`#![cfg(all(unix, feature = "test-timeouts"))]`) and shrinks the deadline to 2 s to exercise the real timeout path end-to-end (deadline → group kill → reader drain → reap → PID clear → work-dir removal). Gates run both `cargo test` and `cargo test --features test-timeouts`. (2) Registry/execution tests use STATIC fixture definitions: an absent-executable fixture for admission tests (discovery can never resolve → no spawn on any machine) and a PATH-fixture shell script for lifecycle integration tests — never a real provider CLI.
**Consequences:** the timeout path is machine-verified in ~2 s instead of documented-but-untested; no automated test can execute a real agent regardless of the host machine's installed CLIs; the feature flag is inert in every shipped configuration (verified: plain `cargo test` compiles the timeout file out entirely).

## D-022 | 2026-11-07 | APPROVED — Both diagnostic adapters disabled (unverifiable read confinement) + backend-authoritative eligibility ledger (Phase 3 Feature 002 security acceptance)
**Context:** the security acceptance confirmed that Codex `--sandbox read-only` bounds WRITES only — the official sandboxing documentation documents no read restriction at all. The newer Codex permissions profiles (`permissions.<name>.filesystem` with read/write/deny and default-deny for ungranted paths) COULD restrict reads, but they are config-file constructs selected via the top-level `default_permissions` key, have no documented per-invocation CLI flag (mixing them with `--sandbox` reverts to the older sandbox settings), and are version-gated (~0.138+): enforcing them would require writing into the user's global Codex configuration (changing the user's unrelated Codex usage) and could not be verified across CLI versions. Claude Code remains disabled for its previously recorded reasons (inherited global configuration, version-dependent tool restrictions, no read-only enforcement in print mode). Separately, execution eligibility was UX-dependent: the frontend "Verified" badge was presentation state.
**Decision:** (1) `supports_safe_diagnostics()` is false for BOTH adapters; no diagnostic process can be started through IPC; each adapter's accurate reason is carried in the capabilities DTO (`diagnosticExecutionNote`) and rendered verbatim in the UI. The documented least-privilege argument constructions (Codex `--sandbox read-only`, Claude `--output-format json` + denied mutating tools) and the truthful `parse_result` contracts remain implemented and fixture-tested for a future re-enable under an independently validated, enforceable sandbox. (2) Execution eligibility is backend-authoritative: `verify_agent` records successful verifications in an `EligibilityLedger` (identity = path + size + mtime + unix inode; failed/missing verification clears the grant); `start_diagnostic_run` — the only caller of `RunRegistry::start` — requires the adapter posture AND a verification no older than 10 minutes (`VERIFICATION_FRESHNESS`); the runner re-checks the discovered executable's path and identity immediately before spawning. Adapter-posture enforcement lives at the IPC boundary (the bypass-proof point); the runner enforces executable identity, which only it can observe at spawn time. (3) The process group is terminated on EVERY run exit path including a normal parent exit (orphaned descendants), with the same documented PID/group-reuse residual risk as D-018.
**Consequences:** no enabled adapter claims stronger filesystem isolation than it enforces (none is enabled); a direct IPC invocation cannot start a diagnostic without a fresh backend verification and an unchanged, re-identified executable; the machinery stays fully tested (fixture-based integration tests prove swapped-executable, impostor-path, and surviving-descendant rejection) so a provider re-enable is a posture change, not a policy change. A successful authenticated provider run remains REQUIRED before any real-provider acceptance; identity checking is best-effort (same-size, same-mtime rewrites within mtime granularity can evade detection).

## D-023 | 2026-11-07 | APPROVED — Codex diagnostics ENABLED on macOS with an app-owned per-run permissions profile (Phase 3 Feature 002 safe Codex adapter completion)
**Context:** D-022 disabled Codex because read confinement appeared to require modifying the user's global configuration. Deeper research (config-basic/advanced docs, CLI help, codex-rs source, and LIVE enforcement probes) corrected that: `-c/--config` overrides are TOML-parsed, sit at the HIGHEST configuration-precedence layer, can define nested tables, and `codex exec` supports `--ignore-user-config` (auth still resolves from `CODEX_HOME`), `--ignore-rules`, and `--ephemeral`. The `codex sandbox` subcommand runs arbitrary commands under the same policy engine provider-free, enabling REAL enforcement verification.
**Decision:** (1) Codex diagnostics are ENABLED on macOS only (`cfg!(target_os = "macos")`), for CLI versions ≥ 0.164.0 (the version the evidence was produced with; unparseable/older versions fail closed at the eligibility gate). (2) Each run defines an app-owned, read-deny-by-default permissions profile entirely via `-c` overrides — `":root"="deny"`, `":minimal"="read"` (documented platform/runtime token), `"/tmp"="deny"` (leaks through `:minimal`), `<work_dir>="write"` — and selects it via `default_permissions`; the profile name carries a per-run random suffix so a collision with user-config entries (which could reopen grants) is impossible. The user's global configuration is NEVER read for policy purposes, NEVER modified, and (via `--ignore-user-config`) not even loaded. (3) The legacy `--sandbox` flag is never passed: mixing it with permissions profiles silently reverts to the legacy write-only sandbox (the fallback trap). (4) Tool-call children get the documented core environment only, with credential-shaped variable names excluded. (5) Claude Code remains disabled (D-022) pending independent review.
**Evidence (provider-free, codex-cli 0.164.0, `codex sandbox` harness; automated in `tests/codex_sandbox_enforcement.rs`, 8/8 passing):** reads inside the work dir succeed; reads of protected files in `$HOME`, `/tmp`, and the macOS per-user temp dir are denied ("Operation not permitted"); writes outside the work dir are denied (no file created); writes inside succeed; an invalid profile value and an unknown profile selection are hard errors (fail closed); network access from tool commands is restricted; a nested `codex sandbox --sandbox-mode danger-full-access` attempt under the confined profile cannot execute (OS-level enforcement covers the whole process tree). The `codex exec` path uses the identical config/profile resolution and accepted the flags in flag-acceptance probes; its end-to-end enforcement still awaits one user-authorized real-provider run.
**Consequences:** a user clicking the diagnostic confirmation runs Codex with reads/writes confined to the app-managed diagnostic directory (plus documented runtime paths); admission, identity re-checks, and the ledger remain intact and unchanged; Linux/Windows stay fail-closed until independently verified; the residual boundary is documented (runtime-token paths are readable by design — `/tmp` re-denied, macOS per-user temp denied by default).
